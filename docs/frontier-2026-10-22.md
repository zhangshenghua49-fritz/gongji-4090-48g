**仓库实测（hf-mirror API）**

- `Lightricks/LTX-2.5`：gated=auto，200.85 GB。**上一轮记错了两个数**：int8-convrot transformer 实为 **21.50 GB**（记 20.03），gemma4-12b TE int8 实为 **15.37 GB**（记 14.32）。

**48G 组合（不自建，用平台预制镜像）**

`Comfy-Org/MiniMax-H3` 逐文件实测字节（这是自建时的唯一正确数字来源）：

```
diffusion_models/            fl2va 与 ref2va 同尺寸
  pruned_w6a8                15,983,746,636   15.98 GB
  pruned_int8_convrot        20,970,379,616   20.97 GB   ← 上一轮记 19.53，错
  pruned_fp8_scaled          20,958,205,608   20.96 GB
  pruned_bf16                40,225,724,176   40.23 GB
  bf16                       66,280,487,368   66.28 GB
  int8_convrot（未剪）        34,038,892,334   34.04 GB
text_encoders/
  qwen3vl_32b_bf16           51,506,295,256   51.51 GB
  qwen3vl_32b_int8_convrot   27,141,342,152   27.14 GB
  qwen3vl_32b_nvfp4_awq      15,687,142,551   15.69 GB   ← 仓内最小档，没得更省
vae/     video_int8 2.81 | video_fp16 5.21 | audio_fp32 0.61
loras/   turbo_4step 1.96 | turbo_8step 1.96
model_patches/ controlnet_union_2.0_pruned_int8 4.53（bf16 8.38）
```

**两个"峰值显存"数字在打架，真正的原因是 TE 放在哪，不是谁算错了：**
- **~27.8 GiB** = 平台预制镜像的口径。`platform-preset-services.md` 原话：**"int8 模型 ~20G + 文本编码器 nvfp4 ~15G 走 CPU offload"** ⇒ TE 不在显存里，峰值落在 denoise 段。
- **42.0 GB** = 全常驻口径（20.97 + 15.69 + 2.81 + 0.61 + LoRA 1.96）。自己搭 ComfyUI 时不设 offload 就是这个数。
- 768p（1344×768 ≈ 0.98MP）激活比模板默认 0.4MP 大，带声时按 **32–36 GB** 预算更保险（估算）。

⇒ 结论：**用平台预制镜像可以吃 27.8GiB 这个便宜（TE 走 CPU）；自建就必须按 42GB 算，48G 才对得上。**

**48G 上的第二选择不是 MAGI-2**：它 README 原话 "NVIDIA Hopper GPUs, 8 of them"，全仓 307GB、preview transformer 228.11GB，1080p 下两 stage 连 80GB 卡都放不下彼此的激活；4bit 仍有 57GB。**48G 上跑不动，排除**。第二选择维持 **LTX-2.5 int8：21.50 + 15.37 + 1.47 + 0.36 = 38.7 GB**。

**TE 选型坑**：4090 是 Ada，nvfp4 只能走 dequant，**没有 FP4 硬件加速**。但仓内 nvfp4_awq（15.69GB）已是最小官方档，int8_convrot（27.14GB）与 denoise 同驻就是 51.5GB > 48。所以只能用它，代价是 TE 编码比 Blackwell 慢。

## 3. 声音：这一格你说得最对

### 3.1 上一轮的错：IndexTTS2 是 2025-09 的模型
GitHub API 实测 `index-tts/index-tts` 只有三个 release：
```
v1.5.0  2025-09-01
v2.0.0  2026-08-13   (IndexTTS-2.0)
v2.5.0  2026-08-13   (IndexTTS-2.5)  ← 现在该用这个
```
平台预制镜像 tag 是 `index-tts:0.3.0` —— **仓库里根本没有 0.3.0 这个 tag**，它极可能是初代 IndexTTS（2025 上半年）的镜像构建号。也就是说平台那个镜像连 2.0 都不是。

### 3.2 但 IndexTTS-2.5 也不是最优 —— VoxCPM2 才是
| 模型 | 体积 | 采样率 | 日语证据 | license | 48G |
|---|---|---|---|---|---|
| **VoxCPM2**（OpenBMB） | **4.62 GB** | **48 kHz** | SIM **0.825**（hifi_clone） | **Apache-2.0 可商用** | ✅ RTF~0.3 |
| Ming-3.0-tts-0.5B | 3.00 GB | 44.1 kHz | SIM 0.765 / CER 3.765 | **MIT** | ✅ |
| IndexTTS-2.5 | 5.49 GB | **22.05 kHz** | 新增日语 + Kana 音素 | bilibili 协议 | ✅ |
| Fish Drama 3 (35B-A3B) | 67.41 / 8bit 39.28 / **4bit 22.15** | — | **日语 CER 2.76 最优** | Community <$50万可商用 | ✅ 4bit |
| dots.tts | 4.81 GB | 48 kHz | SIM **0.838** 最高 / CER 7.16 最差 | Apache-2.0 | ✅ |
| FireRedTTS3 | 19.35 GB | — | SIM 0.825 | Apache-2.0 **但白盒克隆限学术** | ✅ |

**日语音色相似度（克隆因幡巡的唯一关键指标）三张表互证**：dots 0.838 ≈ VoxCPM2 0.825 ≈ FireRedTTS3 0.825 > Ming 0.765。**Ming 强在"克隆综合分 + MIT + 44.1k"，日语保真不是它的格子**（这张表还是 Ming 自己卡里的）。

### 3.3 修正后的配音编队
- **因幡巡（日语少女）**：**VoxCPM2 hifi_clone** —— 48kHz 母带、Apache-2.0、4.62GB、日语 SIM 第一档。参考音 10–20s 干净少女音 + 精确日文 transcript，同一段音同时喂 `reference_wav_path` 和 `prompt_wav_path` 相似度最高。
- **中文旁白**：《钢板与黑麦》的旁白用 **Ming-3.0-tts-0.5B**（MIT / 44.1kHz / zh 最强），且它是唯一在推理参数里用 `language_id` 逐句显式指定语种的 —— 中旁白 + 日台词混排时确定性最高。
- **兜底 A/B**：日语咬字不满意就跑一版 **Fish Drama 3 4bit（22.15GB）**，它是唯一日语 CER 到 2.76 的。
- **IndexTTS-2.5 降为第三顺位**：22.05kHz 输出做 48k 母版要重采样，得不偿失。

## 4. 48G 单卡的真实编队

**关键事实：图像和视频不能同驻。**
- H3 pruned_int8 全常驻 = 20.97 + TE 15.69 + vae 2.81 + audio 0.61 + LoRA 1.96 = **42.0 GB**（768p 带声实际峰值 32–36 GB）
- Qwen-Image-2.1 bf16 = **33.13 GB**
- 两者相加 75GB > 48GB ⇒ **必须分时复用**，不是同机并存。

**编队设计**
| 阶段 | 驻留 | 显存 | 说明 |
|---|---|---|---|
| A 出图 | Qwen-Image-2.1（或 FLUX3 klein 20.3GB） | 33.1 / 20.3 GB | 批量跑分镜关键帧，出完即存盘 |
| B 视频 | H3 pruned_int8 + nvfp4 TE | 39.1 GB | 独占，别的东西一律不驻留 |
| C 配音 | VoxCPM2 4.62 + Ming 3.00 | 7.6 GB | **可与 A 同驻**，不用单独租机器 |

⇒ 一张 4090-48G 就能跑完 A+C；B 单独一轮。不需要两台机器。

## 5. 立刻能做的三步（按性价比排序）

余额 4.01 元 ÷ 3.02 元/h ⇒ **总共只有 1.3 小时机器时间**。所以顺序必须是"先验最便宜的、后跑最贵的"。

**第一步（0 元，本机）**
把因幡巡的参考音切出 10–20s 干净单句日文。这是 VoxCPM2 的唯一输入门槛，没有它后面全白搭。

**第二步（约 0.1 元，3 分钟）**
起一个最便宜的实例，只做一件事：`docker` 内 `huggingface-cli download` 三个小模型验证可达性 —— `OpenBMB/VoxCPM2`(4.62GB)、`inclusionAI/Ming-3.0-tts-0.5B`(3.00GB)、`IndexTeam/IndexTTS-2.5`(5.49GB)。三者都 gated=False，14GB 总下载，跑通即可关。
目的：确认平台能不能拉到这三个 repo（平台走 harbor/公网，这条路上一轮没验过）。

**第三步（约 1 元，20 分钟）**
用平台预制 `MiniMax-H3` 镜像跑一条 4 步 turbo 带声短视频，参数照 `workflows/h3_t2va.json`，但**把权重名从 umt5 改成 Qwen3-VL**（这就是 START-HERE 里的 E 项，一直没改）。带语音音色时步数要 ≥12，不是 8。

**暂缓**：Fibo 2.0（ComfyUI 得等 v0.43）、Hunyuan 保脸工作流（80B 装不下）、 Fish Drama 3（22GB 下载会吃掉 1/4 余额）。
